1. In one paragraph

Every 6 hours (00:17, 06:17, 12:17, 18:17 Pacific), a scheduler starts a fresh Devin session. The session is a fixed nine-step script: eight steps are plain Python commands checked into the repository, one step (triage) is a judgment Devin makes and writes down as data. The script searches seven places (six public sources and Rox's Slack) for new Jev-like models, decides which of the new hits can be run as-is, runs at most ten of them on Modal against the frozen 75-case benchmark, regenerates the leaderboard data and static site, runs the test suite, and pushes one commit straight to main; the site redeploys from it with no merge step.

5. Table 2: the one judgment call (triage)

Table 2. The three verdicts Devin may give a candidate, and what each one triggers.

Triage verdicts
VerdictMeansConsequenceTypical example
runnableThe harness can already call it: a Kev-family or Laya checkpoint on the Hub, or a hosted endpoint whose key is already a Modal secretA run config is written (production + Jev answers + the model, all 75 cases) and it is run today if within the budget of tenA new Kev checkpoint under a different account
needs_adapterA real Jev alternative the harness cannot call yet: new serving stack, new request format, key not provisioned, or over the Kev-27B cost lineRecorded with the missing piece named; nothing runs; shows up on the site's board for Marcus to approve or skipA model that needs a serving framework the harness does not ship
not_jevUnrelated hitRecorded with a one-line reason so it is never re-reviewedA person named Kev; a Laya who is a voice actor

The verdicts are committed as a dated file, so the commit diff is the audit trail of what Devin decided and why. A mechanical checker runs after triage: every candidate must have a verdict, and every runnable verdict must point at an existing config; otherwise the run cannot proceed.
