4. Task 1 — A GGUF decision model answers System One requests on a Modal GPU

Satisfies: R-2.

User story

As the experiment command run by Marcus (or by the daily automation), I want a scoring run whose source is a GGUF file to be answered by a Modal GPU container exactly as a bf16 run is, so that a quantized model's quality, cost and latency land on the dashboard without new evaluation code.

Context

No Modal image in the harness can open a GGUF file, so every GGUF export is triaged needs_adapter. The GGUF runtime now implements the System One endpoint for the official decision-model families itself (plan: Previous steps row 3), so the container only needs to start that server and point the existing posting loop at it (plan: Decided rows 1–3). This is GGUF step 1, the cheapest disconfirming step.

Scope

In scope:

  • One Modal image: CUDA runtime plus the pinned pre-built runtime binary (b11351), plus the harness's runtime dependencies.
  • One Modal function for the gguf engine: download the one named file at the pinned revision into the shared weights volume (tqdm, skipped if cached), start the server with all layers on the GPU and slots equal to the configured concurrency, wait for health, then run the existing API posting loop against localhost and write the usual shard file and shard summary.
  • Load time (download + server start) measured separately from warm time.

Out of scope:

  • Any prompt-building or token-readout code in the harness (plan: Out of scope).
  • The configuration schema (Task 2) and tests (Task 3); this task may be exercised by a hand-built run object.
  • StartLux or any model family the runtime's endpoint does not serve.

Requirements

  • The container fails before starting the server, naming repository and file, when the file is not in the pinned revision.
  • Each response is validated as a System One response; an invalid one is an error, not a silent skip.
  • The shard summary carries GPU type, load seconds, warm seconds and batch count with the same meanings as every local scorer.
  • Progress is visible: tqdm for the download and for the batch loop; shard progress published as today.

Acceptance criteria

  • Given Kev-9B Q4_K_M at its pinned revision and an L40S, when one System One request with one state and several children is posted, then the answers validate and one probability per child is returned.
  • Given a run object with 2 cases, when the function completes, then the runs volume holds a gzipped shard file with a raw record per batch and a shard summary whose warm seconds exclude download and start-up.
  • Given a file name that does not exist in the repository, when the function starts, then it raises naming repository and file and no server is started.
  • Errors and edge cases: the server is not healthy within the start-up budget (fail with the server's last log lines); a 400/422 on a batch larger than one (split, as the API loop already does).

Definition of Done

  • All acceptance criteria pass.
  • R-2 is ✅ in the spec's conformance table at smoke scale, with the conformance suite unchanged (git diff --exit-code tests/test_gguf.py clean).
  • Code is reviewed and merged.
  • Lint, format check and the full test suite pass.
  • No secrets in the image or the repository; image build is reproducible from the pinned build number.
  • Documentation: README source list names gguf.
  • The change is deployed to the Modal app jev-tracker in the rox-research workspace.
  • No unresolved critical defects remain.

Dependencies and constraints

  • Plan constraints: same contract and cost formula (R-2); pinned revision and pinned runtime build; tqdm; no per-model readout code.
  • Assumes the pre-built CUDA binary runs on Modal's L40S driver (unverified until step 1 runs; the fallback is the runtime's own CUDA container image).
  • Plan Open item 1 (does the endpoint batch children into one prefill) is not blocking this task; it is answered by Task 4.

Proof of value

Discharges: Plan → GGUF step 1 — "a Modal GPU container loads Kev-9B Q4_K_M with the pinned runtime build and answers one System One request", falsified if the runtime cannot load the file, rejects our request body, or returns answers that do not validate.

Claim: If every acceptance criterion of this task holds, then GGUF step 1's bar is met.

Premises:

  1. A posted request with one state and several children returns validated answers, one per child — source: this task's Acceptance criteria.
  2. A 2-case run leaves a shard file and a summary with warm seconds excluding load — source: this task's Acceptance criteria.
  3. The request body posted is the one the hosted-API scorer sends today — source: Plan → Decided (reuse the posting loop).
  4. The runtime's endpoint implements System One for Kev — source: Plan → Previous steps row 3 (upstream merge, 2026-10-02).
  5. The pre-built binary runs on the chosen GPU — source: Assumption (unverified).

Argument:

  1. By premise 1 the file loaded and the endpoint accepted our body and answered validly, which is exactly the three failure modes the falsifier names.
  2. By premise 2 the answers were produced by the harness's own loop and summary, so what was proved is the harness path, not a hand test.
  3. Premise 3 means the body tested is the body production runs will send; premise 4 is why the endpoint exists; premise 5 is what makes 1 possible.
  4. Therefore GGUF step 1's bar is met.

Attempted counterexample: the server answers, but with probabilities that are all 0.5 (a wrong prompt template or an unsupported model treated as plain text). Every criterion above still holds. This is a real gap: a criterion is missing.

Falsifier: the 75-case run's kept-mass for the GGUF row is near random (about 0.5) while the bf16 row is 0.753.

Verdict: Open — counterexample found; the missing acceptance criterion is: given the first smoke case, the GGUF answers rank the same children at the top as the committed bf16 Kev-9B answers for that case (spot check, not a tolerance). Added to Task 4's acceptance criteria, where the comparison data exists; this task's verdict becomes Conditional on Task 4 performing that check.

5. Task 2 — A GGUF model is chosen by configuration alone

Satisfies: R-1.

User story

As Marcus editing an experiment configuration, I want to name a GGUF model by repository, revision and file next to the usual method, GPU, shards, concurrency and request limits, so that trying Q8_0 instead of Q4_K_M, or 4B instead of 9B, is a one-line edit and not a code change.

Context

Every existing source is a configuration type with a fixed set of fields that the experiment loader turns into a scoring run (plan: Decided row 5). A GGUF source needs one new field, the file inside the repository, and the loader must carry it to the run and to the run's name so Q4 and Q8 rows are distinguishable. This is the configuration half of GGUF step 2.

Scope

In scope:

  • A gguf source type: model (repository@revision), file, method, gpu, shards, concurrency, max_items, max_chars, with the same defaults as the Kev source.
  • The scoring run carries the file; its name includes the file stem; its engine is gguf; dispatch maps the engine to Task 1's function.
  • README: gguf in the list of sources with the configuration shape.

Out of scope:

  • Registry or site changes: a GGUF row is labelled through the existing registry file like any other run.
  • A GPU table entry per GGUF repository; the GPU is a configuration value for this source (a default is allowed).

Requirements

  • A gguf source without file fails to load with a message naming the field.
  • The run name distinguishes two files of the same repository.
  • No existing source's parsing changes.

Acceptance criteria

  • Given the smoke configuration, when only file changes from the Q4_K_M file to the Q8_0 file, then the loaded run's file and name change accordingly and nothing else does.
  • Given a gguf source with no file, when the configuration is loaded, then loading fails and the message names file.
  • Given a scoring run with engine gguf, when a shard is spawned, then the GGUF function is the one called.
  • Errors and edge cases: model without @revision is accepted (the pin is a constraint of the plan, enforced by review, as for other sources); an unknown GPU name fails at cost time with the name, as today.

Definition of Done

  • All acceptance criteria pass.
  • R-1 is ✅ in the spec's conformance table with the conformance suite unchanged.
  • Code is reviewed and merged.
  • Lint, format check and the full test suite pass.
  • README updated.
  • The change is deployed to the Modal app jev-tracker (the dispatch table ships with the app).
  • No unresolved critical defects remain.

Dependencies and constraints

  • Interface shared with Task 1: the run object's engine literal gguf and its file field; agreed before the wave starts so both tasks compile against it.
  • Plan constraint: configuration is the source of truth for tunable values.

Proof of value

Discharges: Plan → GGUF step 2 — "a quantization switch needs a code edit" is the falsifier.

Claim: If every acceptance criterion of this task holds, then switching model, size or quantization needs no code edit.

Premises:

  1. Changing file alone changes the run's file and name — source: this task's Acceptance criteria.
  2. A missing file is a configuration error — source: this task's Acceptance criteria.
  3. Engine gguf dispatches to the GGUF function — source: this task's Acceptance criteria.
  4. The GGUF function reads repository, revision and file from the run, not from constants — source: Task 1 Scope.

Argument:

  1. By 1 and 4 the file the container fetches is the configured one; by the same route model selects repository and size.
  2. By 3 the configured source reaches that function without a code path per model.
  3. By 2 a configuration that could not select a file is rejected rather than silently defaulting.
  4. Therefore a switch is a configuration edit.

Attempted counterexample: a repository whose GGUF needs a different GPU than the default (Kev-27B Q4 would not fit an L40S). The switch still needs no code edit because gpu is a configuration field; it needs a second line edited. Not a counterexample.

Falsifier: a future GGUF repository that needs a model-specific server flag (for example a different chat template) and so a code change.

Verdict: Proved for the official Kev GGUF repositories; the falsifier names when to revisit.

  • Technical specification: docs/GGUF_SPEC.html R-1.
  • Related issues: Task 1 (parallel), Task 3 (depends on this).

6. Task 3 — The GGUF path is proven without a GPU and has a smoke configuration

Satisfies: R-3 (and it is the GPU-free conformance suite of R-1 and R-2).

User story

As the CI pipeline, I want the GGUF configuration parsing, dispatch and response conversion covered by tests that need no GPU, and a 2-case smoke configuration committed, so that a regression is caught on every pull request and the first Modal run has a known input.

Context

The spec maps one scenario to one test, named for its requirement (R-1, R-2, R-3). The harness's existing tests build request bodies and convert answers without a model; the same style applies here. The smoke size is 2 cases, the existing smoke size (plan: Decided row 7).

Scope

In scope:

  • tests/test_gguf.py: test_R12_switch_quantization, test_R12_missing_file, test_R10_dispatch, test_R10_response_validates (a recorded server response validates and records like an API response).
  • configs/kev9b_gguf_smoke.yaml: 2 cases, production, Jev answers, and Kev-9B Q4_K_M on an L40S.

Out of scope:

  • Running anything on Modal (Task 4).
  • Rescoring tests for the smoke experiment (they attach once the experiment is committed).

Requirements

  • Tests run in the existing suite command with no network and no GPU.
  • Each test is one scenario from the spec, GIVEN/WHEN/THEN as comments.
  • The smoke configuration loads and its run object names the file and GPU.

Acceptance criteria

  • Given the repository, when the suite runs, then the four tests pass and the whole suite stays green.
  • Given the smoke configuration, when it is loaded, then its GGUF run has 2 cases, the Q4_K_M file and GPU L40S.
  • Errors and edge cases: a test must not download the GGUF file; a fixture holds the recorded response.

Definition of Done

  • All acceptance criteria pass.
  • R-1, R-2 and R-3 rows in the conformance table name these tests; suite committed unchanged afterwards.
  • Code is reviewed and merged.
  • Lint, format check and the full test suite pass in CI.
  • Spec conformance table updated.
  • The change is deployed with the pull request (no runtime deployment).
  • No unresolved critical defects remain.

Dependencies and constraints

  • Depends on Task 1 (function to dispatch to, response shape) and Task 2 (source type).
  • Spec rule: tests are drafted by Devin, owned by Marcus; once committed they are not edited to pass.

Proof of value

Discharges: Plan → GGUF step 2 — "config parsing or dispatch tests fail" is the falsifier.

Claim: If every acceptance criterion holds, then the configuration and dispatch path of GGUF step 2 is proven without a GPU and R-3 holds.

Premises:

  1. The four scenario tests pass in the normal suite — source: this task's Acceptance criteria.
  2. The smoke configuration loads to the expected run — source: this task's Acceptance criteria.
  3. One scenario is one test named for its requirement — source: spec-doc rule.

Argument:

  1. By 1 and 3 each R-1/R-2 scenario that can be checked without a GPU has a test that passes.
  2. By 2 the input of GGUF step 3 is a committed, loadable configuration.
  3. Therefore step 2's falsifier did not fire and the suite exists.

Attempted counterexample: the tests pass against a recorded response, but the live server's response shape differs from the recording. The criteria hold and the path still breaks. This is why R-2's first scenario is bound to the Modal smoke run (Task 4), not to this task alone.

Falsifier: Task 4's run fails on response validation while this suite is green.

Verdict: Conditional on the recorded response being taken from the real server in Task 1 (listed in Dependencies).

7. Task 4 — The first GGUF cost and latency numbers stand beside bf16

Satisfies: R-2 at smoke scale (its "one request answered" and "same shard files" scenarios), which is the G-2 measurement.

User story

As Marcus deciding whether GGUF is worth a 75-case run, I want the 2-case smoke experiment run on Modal and its load seconds, warm GPU-seconds per query and $/1k reported next to the bf16 Kev-9B row, so that I can approve or stop the full run on a measured number.

Context

This is GGUF step 3, the first step that bills a GPU and the one that answers the plan's hypothesis cheaply (under $1). The bar is the bf16 row: $5.6/1k and 5.1 GPU-s per query on an H100. It also answers plan Open item 1 (does the endpoint batch children) through the per-query warm time.

Scope

In scope:

  • Run the smoke configuration on Modal with tqdm visible; pull; evaluate.
  • Report: load s, warm GPU-s per query, $/1k, GPU, beside bf16 Kev-9B's committed numbers; plus the spot check from Task 1's proof (top children of case 1 agree with bf16).
  • Commit the experiment folder (config as run, calls, raw answers, kept-mass, costs, latency) and a registry row labelled with the file.

Out of scope:

  • The 75-case run (GGUF step 4, on Marcus's go).
  • Any quality claim from 2 cases: kept-mass at 2 cases is a smoke signal, not a result.

Requirements

  • Cost uses the shared formula: warm GPU-seconds × the GPU's list price, extrapolated to 1k queries.
  • The report states which numbers are from 2 cases and which from 75.
  • A refuted hypothesis (GGUF slower and dearer) is reported as a result, not hidden.

Acceptance criteria

  • Given the smoke configuration, when the run completes, then the experiment folder has the GGUF row's raw answers for 2 cases and the cost table shows GPU, $/1k and s/query for it by the same formula as the bf16 row.
  • Given case 1, when the GGUF and committed bf16 answers are compared, then the top-ranked children agree (spot check; a disagreement is reported, not a failure).
  • Given the report, when Marcus reads it, then it names load s, warm GPU-s/query and $/1k for GGUF beside bf16's, and states the 2-case caveat.
  • Errors and edge cases: a shard failure is reported with the server's last log lines; the run is respawnable from the recorded calls as today.

Definition of Done

  • All acceptance criteria pass.
  • R-2 is ✅ at smoke scale (bound to the smoke experiment's shard files and cost table), with the conformance suite unchanged.
  • Experiment folder and registry row reviewed and merged.
  • Full test suite (which rescores committed experiments) passes.
  • Plan status line and Previous steps updated with the step 3 row and its pointer.
  • The change is deployed as committed data in the repository; the dashboard row appears after site regeneration (existing step).
  • No unresolved critical defects remain.

Dependencies and constraints

  • Depends on Task 3 (configuration and tests merged) and so on Tasks 1 and 2.
  • Plan constraint: smoke first, 75 only on Marcus's go; GPU budget under $1 for this task.
  • Modal credentials and the shared weights volume must be reachable from the session.

Proof of value

Discharges: Plan → GGUF step 3 — "report load s, warm GPU-s per query and $/1k beside bf16 Kev-9B"; falsified if the GGUF row is neither cheaper nor faster, or its cost cannot be computed by the shared formula.

Claim: If every acceptance criterion holds, then Marcus has the measured comparison GGUF step 3 promises, computed comparably (R-2: same shard files, same evaluator).

Premises:

  1. The cost table shows the GGUF row with GPU, $/1k and s/query by the shared formula — source: this task's Acceptance criteria.
  2. The report names the three numbers beside bf16's and the 2-case caveat — source: this task's Acceptance criteria.
  3. The spot check on case 1 is reported — source: this task's Acceptance criteria.
  4. Load time is excluded from $/1k for every local scorer — source: Plan → Decided row 6.
  5. Per-query warm time at 2 cases predicts per-query warm time at 75 — source: Assumption (unverified; warm time per query is roughly constant once the server is loaded).

Argument:

  1. By 1 and 4 the GGUF cost is computed exactly as the bf16 cost was, so the two rows are comparable (R-2).
  2. By 2 the comparison reaches Marcus in the shape the step promises, with its scale stated.
  3. By 3 the answers are shown to be model answers, not a degenerate readout (closes Task 1's Open verdict).
  4. By 5 the number is informative about the 75-case run that the decision is about.
  5. Therefore GGUF step 3 is discharged, whichever way the number falls.

Attempted counterexample: with 2 cases and concurrency 1, the server never has more than one request in flight, so per-query time understates what a batched 75-case run would achieve, or overstates it if the endpoint serialises children. The criteria hold, the comparison is still fair (bf16's smoke would have the same shape), but premise 5 is weak.

Falsifier: the 75-case run's warm GPU-s per query differs from the smoke run's by more than the bf16 model's own smoke-to-full difference.

Verdict: Conditional on premise 5 (listed in Dependencies as "smoke per-query time is indicative"); the report must say so.
