3. Purpose and goals

The harness scores every decision model through one contract (System One: one child per question, noul = probability of "yes" or score = expected ordinal level) and derives quality, cost and latency from the saved answers. Every local model so far was loaded as bf16 safetensors through its own Python package; no image can open a GGUF file. A GGUF file is the same model with quantized weights (for example 4-bit): less GPU memory, so a cheaper GPU and possibly lower latency. Marcus's words: "running these using GGUF could help us reduce cost + improve latency". The goals the requirements cover:

  • G-1 Run a quantized GGUF decision model through the 75-case benchmark on Modal, same contract and metrics.
  • G-2 Compare its cost ($/1k) and latency against the bf16 run of the same weights already on the dashboard.
  • G-3 Smallest change; first reviewable number within one session.

4. Requirements

R-1

R-1 — source: gguf in the experiment YAML

unbound

Level 2 · experiment configuration · serves R-2 · covers G-1.

An experiment configuration SHALL accept a reranker with source: gguf, model: <repo>@<sha> (for example ggml-org/Kev-9B-GGUF@<sha>) and file: <name>.gguf (for example Kev-9B-Q4_K_M.gguf), plus the existing method, gpu, shards, concurrency, max_items and max_chars fields, and turn it into a scoring run for the GGUF scorer.

Scenario: switch quantization

  • GIVEN the smoke configuration for Kev-9B Q4_K_M
  • WHEN only file is changed to Kev-9B-Q8_0.gguf
  • THEN the loaded run carries the Q8_0 file, its name shows it, and nothing else changes

Scenario: a missing field is a configuration error

  • GIVEN a gguf source with no file
  • WHEN the configuration is loaded
  • THEN loading fails with a message naming file

Scenario: dispatch

  • GIVEN a scoring run whose engine is gguf
  • WHEN a shard is spawned
  • THEN the GGUF scorer function is the one called, with the configured GPU
R-2

R-2 — One Modal function score_cases_gguf

unbound

Level 1 · Modal app · root · covers G-1, G-2.

The Modal app SHALL have one GGUF scorer function whose image is a CUDA runtime plus the llama.cpp b11351 binary; it SHALL download the named .gguf into the shared HF-cache volume (tqdm), start llama-server --parallel <concurrency>, reuse the score_cases_api posting loop against localhost, and write the same shard files every local scorer writes, so that kept-mass, warm GPU-seconds, $/1k and latency come from existing code.

Scenario: one request answered

  • GIVEN Kev-9B Q4_K_M at its pinned revision on an L40S
  • WHEN one System One request with one state and several children is posted
  • THEN the response validates as a System One response with one probability per child

Scenario: the same shard files

  • GIVEN a 2-case run
  • WHEN the function finishes
  • THEN the runs volume holds a gzipped shard file with a raw record per batch and a shard summary (GPU, load s, warm s, batches) with the same meanings as every local scorer, so the existing evaluator prices and times it with no new code

Scenario: a wrong file name

  • GIVEN a configuration whose file does not exist in the pinned revision
  • WHEN the function starts
  • THEN it fails naming repository and file, before the server is started
R-3

R-3 — A 2-case smoke config and GPU-free unit tests

unbound

Level 2 · configs, tests · serves R-2 · covers G-3.

The repository SHALL contain a 2-case smoke configuration for Kev-9B Q4_K_M on an L40S, and unit tests for GGUF configuration parsing and scorer dispatch that run in the normal suite with no GPU and no network.

Scenario: the suite stays green

  • GIVEN the repository
  • WHEN the test suite runs on a CPU-only machine
  • THEN the GGUF tests pass and nothing downloads a model

Scenario: the smoke config is runnable

  • GIVEN the smoke configuration
  • WHEN it is loaded
  • THEN its GGUF run has 2 cases, the Q4_K_M file and GPU L40S, beside production and Jev

5. Not required

Deleted from the proposal by minimal-cover, with the reason, and approved as deletions.

  • A generic llama-cpp-python adapter with per-model prompt and readout. llama-server already does it for five decision-model families (Kev, Laya, Lev, OpenJev, Julia-1).
  • StartLux GGUF. Its GGUF is a bare decoder; the readout lives in their torch gguf_server.py. Separate follow-up if wanted.
  • ONNX, crawler/triage rule changes, dashboard changes. Not needed for G-1..G-3.
  • A quality bar for the GGUF row. Whether quantization costs kept-mass is what the run measures; it is a hypothesis, not a gate (noise about ±0.02 at 75 cases).

6. Clarifications

None. The four flags raised with the proposal (smoke size 2, pin b11351, Kev-9B Q4_K_M on L40S first, GGUF-may-still-lose-on-latency hypothesis) were approved as-is and are recorded as decisions in docs/GGUF_PLAN.html.
