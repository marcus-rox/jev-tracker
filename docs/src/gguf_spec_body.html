3. Purpose

The harness scores every decision model through one contract (System One: one child per question, noul = probability of "yes" or score = expected ordinal level) and derives quality, cost and latency from the saved answers. Until now every local model was loaded as bf16 safetensors through its own Python package. A GGUF file is the same model with its weights quantized (for example 4-bit), which needs less GPU memory and may run on a cheaper GPU, faster. This slice lets a GGUF export of a decision model be named in an experiment configuration and scored on Modal exactly as a bf16 model is, so that the dashboard can show the two as comparable rows.

4. Requirements

R-10

R-10 — GGUF scoring

unbound

Level 2 · Modal scorer for GGUF · serves R-1 · also serves R-2, R-3.

experiment run SHALL score a quantized GGUF export of a decision model, named in the configuration by its Hub repository pinned to a revision and the file inside it, on the benchmark cases on Modal, through the System One contract, and leave the same artifacts a bf16 run leaves (raw answers, kept-mass, cost, latency).

Scenario: a GGUF smoke run

  • GIVEN a configuration with a gguf source naming Kev-9B Q4_K_M and cases: 2
  • WHEN experiment run finishes
  • THEN one experiment directory holds that model's raw answers for both cases and a kept-mass table beside production and Jev

Scenario: the answers are indistinguishable downstream

  • GIVEN the GGUF run's raw answers and the bf16 run's raw answers for the same model
  • WHEN both are loaded by the evaluator
  • THEN they validate through the same types and give the same keys per case (R-2 holds)

Scenario: a wrong file name

  • GIVEN a configuration whose file does not exist in the named repository
  • WHEN the run starts
  • THEN it fails naming the repository and the file, before any question is answered
R-11

R-11 — Comparable cost and latency

unbound

Level 3 · Modal scorer for GGUF, cost tables · serves R-10.

A GGUF run's cost and latency SHALL be measured the same way as a local bf16 run's: cost from warm GPU-seconds times the GPU's list price, latency as GPU-seconds per query, with the GPU named on the row.

Scenario: two rows for one model

  • GIVEN a Kev-9B Q4_K_M run on an L40S and the committed Kev-9B bf16 run on an H100
  • WHEN the cost and latency tables are generated
  • THEN both rows show $/1k queries and s/query computed by the same formula, each naming its GPU

Scenario: model loading is not billed as answering

  • GIVEN a GGUF shard that spent time downloading and loading the file before the first answer
  • WHEN its cost is computed
  • THEN load time is reported separately and only warm time enters $/1k, as for every other local scorer
R-12

R-12 — Choice by configuration

unbound

Level 3 · Experiment configuration · serves R-10.

Choosing a different GGUF model, size or quantization SHALL require only a configuration edit: repository, revision, file, method, GPU, shards, concurrency and request limits are all configuration values, and no code changes.

Scenario: switch quantization

  • GIVEN the smoke configuration for Kev-9B Q4_K_M
  • WHEN only the file name is changed to the Q8_0 file
  • THEN the run proceeds with Q8_0 and the run's name shows the new file

Scenario: a missing field is a configuration error

  • GIVEN a gguf source with no file named
  • WHEN the configuration is loaded
  • THEN loading fails with a message naming the missing field

5. Not required

  • A per-model prompt and readout adapter inside the harness. The runtime used to serve GGUF files already implements the System One readout for the official decision model families (Kev, Laya, Lev, OpenJev, Julia-1); the harness only posts its existing requests.
  • StartLux GGUF exports. Their GGUF is a bare decoder; the readout lives in the publisher's own serving code. A separate slice if wanted.
  • ONNX and MLX exports. Different runtimes, and most hits are repackagings of models already benchmarked in bf16.
  • Crawler, triage rule, queue and dashboard changes. Not needed for the goals G-1..G-3 of the proposal; a GGUF row appears on the dashboard through the existing registry.
  • A quality bar for the GGUF row. Whether quantization costs kept-mass is the question the run answers; it is a hypothesis, not a gate (benchmark noise is about ±0.02 at 75 cases).
