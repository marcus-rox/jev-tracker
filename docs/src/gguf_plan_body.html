2. The objective

A quantized GGUF export of a decision model already on the dashboard in bf16 can be named in a configuration and scored on Modal on all 75 cases, and its row shows cost and latency measured the same way as the bf16 row. The bar it must beat is the bf16 run of the same weights: Kev-9B bf16 on an H100 (80 GB), the cheapest committed run that beats production, at $5.6 per 1k queries and 5.1 GPU-seconds per query (kept-mass@50 0.753). Success, falsifiably: the Kev-9B Q4_K_M row is cheaper per 1k queries or faster per query than that bf16 row while its kept-mass stays within the benchmark noise (about ±0.02 at 75 cases). If it is neither, the hypothesis "GGUF reduces cost or latency" is refuted for this model, which is a valid outcome and is recorded as such.

5. Constraints

  • Same contract, same artifacts, same cost formula as every local scorer. Prevents an incomparable row: a GGUF number computed differently from the bf16 number would answer nothing (the reason the project exists).
  • Pin the Hub revision of the GGUF repository. Kev-27B's weights moved under an unpinned run on 2026-09-30 and shifted kept-mass by about 0.01; the GGUF exports are re-converted when their source moves.
  • Pin the runtime build. The System One endpoint in the GGUF runtime is one day old; an unpinned "latest" would make reruns irreproducible.
  • tqdm for the file download and the batch loop (Marcus, standing): a silent 6 GB download looks like a hang.
  • Smoke first (2 cases), then all 75 only on Marcus's go. Prevents a $3 run that fails on request shape; the smoke run costs under $1.
  • No per-model readout code in the harness. The rox-research llama.cpp fork (2026-09-29) cost a session of adapter work and was 10× slower than Kev's server; if the runtime's own endpoint does not serve a model, that model is out of scope here.

8. Decided

  • Serve GGUF through the runtime's own System One endpoint, not a per-model adapter. Upstream llama.cpp implements the prompt and readout for the official decision families; writing our own would repeat the rox-research fork and lock us to one model.
  • Runtime built from a pinned upstream commit (master of 2026-10-02 18:26 UTC) inside the Modal image, not the Python binding. Superseded decision: the pre-built release binary (b11351). Falsified by step 1: the System One endpoint was merged upstream at 09:56 UTC but the newest release was cut from an 08:08 commit, so no pre-built binary can load the official decision-model GGUFs yet ("wrong number of tensors; expected 429, got 427", the two being the decision head). The source build is a one-time image cost; switch back to a release binary once one ships. The binding would add a second readout path.
  • Reuse the hosted-API posting loop against localhost. It already validates responses, retries, splits oversized batches and writes the shard file; the GGUF scorer only starts the server first.
  • First target Kev-9B Q4_K_M on an L40S (48 GB). The bf16 run needed an H100 and is the cheapest committed row that beats production; a 4-bit file fits a GPU at half the price.
  • Configuration shape: model: <repo>@<revision> plus file: <name>.gguf, mirroring how bf16 sources pin a revision; the run name carries the file so Q4 and Q8 rows are distinguishable.
  • Load time excluded from $/1k, as for every local scorer. Download and server start-up are reported as load seconds; warm seconds start at the first request.
  • Smoke size 2 cases, the existing smoke size, not a new number.

9. Out of scope

  • StartLux GGUF: bare decoder, readout in the publisher's torch server; separate task.
  • ONNX and MLX exports: other runtimes; nearly all are repackagings of benchmarked bf16 models.
  • A generic per-model prompt/readout adapter.
  • Crawler and triage rule changes (re-triaging the 181 export hits), queue, dashboard, data/, site/dist.
  • Kev-27B GGUF: the 27B serving question was closed in rox-research; revisit only if 9B shows a clear win.

10. Open

  • Does the runtime's System One endpoint batch many children of one state into one prefill? Resolved by GGUF step 3's warm GPU-s per query: if a 25-child request costs about 25 single-child requests, latency will not beat Kev's server.
  • Does 4-bit quantization move Kev-9B's kept-mass outside the ±0.02 noise? Resolved by GGUF step 4 (all 75 cases). Not a gate; a result either way.
  • Which GPU is the right cost line for GGUF rows (cheapest that fits, or the bf16 row's GPU)? Decided for now as "cheapest that fits" (L40S); Marcus to confirm when the first number lands.
